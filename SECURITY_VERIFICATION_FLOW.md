# Verification flow

The bot generates the user-facing short URL itself by calling an enabled shortener configured in `/panel`, using that provider's saved API key. It sends only the actual short URL returned by the provider. Disabled or incomplete shortener entries are never used; if several providers are enabled, one is selected randomly unless `/verify N` pins a provider.

## Base URL enabled

1. Bot creates a unique, expiring `verify_TOKEN` record.
2. Bot calls an enabled shortener API with its saved API key. The destination is the backend `/shortener-complete?token=...&sid=...` callback.
3. User completes the generated shortlink and is returned to the backend callback.
4. Backend checks that the token exists, has not expired, belongs to the selected enabled shortener, and passes that shortener's optional Referer policy.
5. Backend marks the web step complete and displays a link to `telegram.me/BOT_USERNAME?start=verify_TOKEN`.
6. Telegram bot validates the same token and user ID before granting access.

## Base URL disabled

1. Bot creates a unique, expiring `verify_TOKEN` record.
2. Bot calls an enabled shortener API with its saved API key. The destination is `telegram.me/BOT_USERNAME?start=verify_TOKEN`.
3. After completing the shortlink, the user returns to Telegram.
4. Bot validates the same token and user ID before granting access. No public web server is needed.

## Verification disabled

The shortener and verification flow is skipped; the bot delivers the requested content directly.

## Security notes

- The shortener URL is taken from the provider API response; the bot must not fabricate a short URL.
- Token expiry and user-ID matching are enforced by the Telegram bot.
- In Base URL mode, the backend validates the selected enabled shortener and optionally checks its Referer host when Referer protection is enabled. Referer headers are not cryptographic proof and may be omitted by some browsers/providers.
- A user who can extract the final destination from a shortener can potentially bypass provider-side completion; robust proof requires a provider-signed callback/webhook or provider-side completion API. Treat Referer checking as an additional signal, not a guarantee.
- Use HTTPS and a stable, high-entropy `SESSION_SECRET_KEY` for the backend. Never commit API keys or credentials.


## Anti-Bypass Shield shortener API compatibility

Filestore can also use the dedicated shortener-generation API exposed by the
Anti-Bypass Shield project. In `/panel` → Shorteners (or `/addshortener`), add
the Anti-Bypass deployment's **base URL** and the dedicated per-shortener API
key generated by that platform. Do not use the account master key or the
underlying provider's private API key.

Supported API shapes:

- `GET /api?api=DEDICATED_KEY&url=DESTINATION&format=text&unprotected=1`
- `GET /st?api=DEDICATED_KEY&url=DESTINATION&format=text&unprotected=1`
- `GET /api/get_shortener_url?token=DEDICATED_KEY&st=DEDICATED_KEY&direct=1&unprotected=1&url=DESTINATION`

Filestore sends the token-specific verification destination as `url`. The
Anti-Bypass API validates that the dedicated key belongs to the selected
configured shortener, calls that shortener's real provider API, and returns
the generated URL. Filestore accepts its plain-text URL response or JSON
`shortenedUrl` response (including supported nested response objects). The
returned provider URL is what the Telegram user receives.

`unprotected=1` tells the Anti-Bypass API not to add a second, nested Anti-Bypass
verification gate. It does not disable the provider's shortlink generation or
the Filestore `verify_TOKEN` validation. Filestore still validates the token
and user identity after the shortener redirects to the supplied destination.
